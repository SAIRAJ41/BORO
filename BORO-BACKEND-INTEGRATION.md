# BORO Backend Integration

## Private ownership-document storage

Ownership documents are stored in the private Supabase Storage bucket
`ownership-documents`. Browser code never receives the service-role key. The
server uses `@supabase/supabase-js` with the service-role key, stores a
listing-scoped random storage path and file metadata in PostgreSQL, and never
stores or exposes a public URL.

Required server environment variables:

- `DATABASE_URL`
- `SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`

The service-role key must exist only in the server environment and must never
be committed or exposed to client-side code.

## Upload and retrieval

- `POST /owner/spaces`
- `POST /owner/spaces/:id`
- `GET /owner/spaces/:id/document`
- `GET /admin/listings/:id/document`

Owner upload and update routes require an authenticated owner session and
verify listing ownership in the service layer. Admin retrieval requires an
authenticated admin session. Document retrieval returns a signed URL valid for
five minutes. Public discovery and ordinary user responses do not include
storage paths.

New listings require an ownership document before submission. A rejected
listing requires a replacement document when resubmitted. Uploading a
replacement does not approve the listing. A new document is uploaded before
the database update; if the update fails, the existing document remains
untouched.

Accepted formats are PDF, JPEG, and PNG. The upload is limited to 10 MB,
checks the extension and declared MIME type, and verifies the file signature
for the supported formats. Storage uploads use unique non-overwriting paths
under the listing ID.

## Local setup and deployment

1. Add the required environment variables to the server environment without
   printing them or committing them.
2. Create a private Supabase Storage bucket named `ownership-documents` in the
   Supabase Dashboard.
3. Generate the Prisma client:

   ```text
   npx prisma generate --config prisma7.config.ts
   ```

4. Review the additive migration SQL in
   `prisma/migrations/20261031210000_add_private_ownership_document_metadata/migration.sql`.
5. Apply the migration only through an approved deployment process.

The migration has not been applied by this milestone, and no real bucket or
file was created or modified.

## Remaining limitations

- The admin listing review UI is not implemented.
- State-changing browser routes use per-session CSRF tokens generated by
  `middleware/csrf.js`; missing and invalid tokens are rejected. Multipart
  routes validate the token after multer parses the form. Login, signup,
  logout, demo login, booking, owner, and admin forms include hidden tokens.
- Existing legacy `ownership_document_url` data is preserved for migration
  compatibility but is not used for new uploads or returned by normalized
  listing responses.
- The new migration must be reviewed and applied before live uploads can work.

## Admin listing review workflow

Admin users review listings at `GET /admin/listings`, with optional
`status=pending`, `status=approved`, or `status=rejected` filtering. Individual
reviews are available at `GET /admin/listings/:id`. Both pages require the
existing authenticated-admin route guard.

Admins can approve or reject pending listings through:

- `POST /admin/listings/:id/approve`
- `POST /admin/listings/:id/reject`

Approval sets the listing to `approved`, activates it, records `reviewedAt`
and the authenticated admin ID, and clears any rejection reason. Rejection
requires a meaningful server-validated reason, sets the listing to `rejected`
and inactive, and records the reviewer, timestamp, and reason. State checks
are repeated in the service transaction, so approved or rejected listings
cannot be reviewed again.

Admins can request a five-minute signed document URL through
`GET /admin/listings/:id/document`. Owners can request documents only for
their own listings. Signed URLs, storage paths, and private metadata are not
included in public listing responses.

Owners see each listing's pending, approved, or rejected state in
`/owner/my-spaces`. Rejection reasons are shown only on the owner's own
listing. Corrected listing information and a replacement document resubmit a
rejected listing as pending and clear the previous review metadata; approval
never occurs automatically. Listing decisions are written to the existing
audit log with the authenticated admin actor and listing metadata.

Owners can view their own listings in every lifecycle state at
`GET /owner/spaces/:id`. The service scopes the database query by both the
listing ID and the authenticated owner's ID; another owner's listing and
nonexistent listings return the not-found response. The private detail page
shows property, review, status, rejection, and document metadata without
exposing storage paths.

When a document is present, the detail page links to
`GET /owner/spaces/:id/document`, which authorizes the owner or an admin and
returns a five-minute signed URL. Missing documents show a safe message and no
retrieval link. The listing overview links to this private detail page rather
than the public listing route.

Owner listing detail tests cover pending, approved, and rejected listings,
cross-owner and missing-listing access, missing documents, and signed-document
retrieval. Route regression coverage includes the owner detail page.

## Owner booking requests and calendar reads

`GET /owner/requests` now reads pending requests through
`bookingService.getOwnerRequests(ownerId)`. The service filters bookings through
their related space owner, and returns the booking, requester, payment,
purpose, and slot fields expected by the existing EJS view.

`GET /owner/calendar` now reads through
`bookingService.getOwnerCalendar(ownerId)`. The route flattens the service's
seven-day `bookingsByDay` result into the existing calendar view shape. The
service excludes cancelled, rejected, and waitlisted bookings and preserves
date, time, status, space, requester, and purpose data. Hardcoded mock
bookings and conflict examples are no longer used by these pages; conflict
actions remain unchanged for a later step.

The owner ID is always taken from the authenticated owner session. Empty
results render the existing empty states, and database query errors use the
application error handler. Focused read tests cover owner scoping, booking
and slot data, and empty calendars.

## Owner booking approval and rejection

The existing owner forms post to:

- `POST /owner/requests/:id/approve`
- `POST /owner/requests/:id/reject`

These routes now call `bookingService.approve(bookingId, ownerId, reason)` and
`bookingService.reject(bookingId, ownerId, reason)`, using only the
authenticated owner session for `ownerId`. The service verifies the booking's
related space belongs to that owner and only permits the `requested` state.

Approval remains transactional and preserves overlap checks, booking status,
PIN generation, cancellation fields, notifications, and audit logging.
Rejection remains transactional and preserves reason validation, payment and
deposit refund behavior, slot release, waitlist promotion, notifications, and
audit logging. Route failures are shown through the existing flash-message
pattern and redirect back to the request queue. Waitlist and other owner
mutation routes remain unchanged.

Focused action tests cover successful approval and rejection, ownership
isolation, invalid and repeated transitions, slot consistency, and audit
records.

## Owner dashboard read pages

The following authenticated owner GET routes now use owner-scoped database
reads:

- `GET /owner/today` uses `bookingService.getOwnerToday(ownerId)`.
- `GET /owner/incidents` uses `incidentService.getOwnerIncidents(ownerId)`.
- `GET /owner/history` uses `bookingService.getOwnerHistory(ownerId)`.
- `GET /owner/earnings` uses `bookingService.getOwnerEarnings(ownerId)`.

Booking queries filter through `space.ownerId`; incident queries filter by
`ownerId`. The owner ID comes from the authenticated session, never request
input. Empty results use the existing EJS empty states, and existing POST
mutation routes remain unchanged.

History includes completed, closed, cancelled, and rejected bookings. Earnings
are calculated from stored completed/closed booking amounts (`hourlyFee`,
`platformFee`, and `netPayout`) and stored availability-slot counts. The
schema has no payout-transfer history model, so the earnings page displays the
stored booking ledger when no actual payout records exist; it does not invent
payout transfers. Focused tests cover owner isolation, operations data,
incident normalization, earnings calculations, and empty results.

## Owner availability slot management

The owner calendar now includes availability CRUD through:

- `GET /owner/calendar` for owner-scoped bookings and slots.
- `POST /owner/availability` to create a slot.
- `POST /owner/availability/:id` to update an eligible slot.
- `POST /owner/availability/:id/delete` to delete an eligible slot.

These routes use `bookingService.getOwnerAvailability`,
`createAvailabilitySlot`, `updateAvailabilitySlot`, and
`deleteAvailabilitySlot`. Space ownership is checked in the service using the
authenticated owner ID, and only approved active listings are eligible.

Dates must be valid, non-past `YYYY-MM-DD` values and times must be valid
`HH:MM` values with start before end. Duplicate and overlapping slots are
rejected. Existing bookings are checked by space, date, and time; booked or
reserved slots cannot be edited or deleted. Create and update operations use
serializable transactions so concurrent overlapping creates cannot both
succeed. Successful create, update, and delete operations write transaction-
local audit records. The existing booking creation and slot reservation logic
is unchanged.

Focused availability tests cover ownership, lifecycle eligibility, validation,
overlap and booking conflicts, booked-slot protection, audit records, and
concurrent creation.

## Availability edge-case verification

Slot date inputs are parsed as date-only UTC values and compared with the
server's local calendar date key, so persistence does not shift a submitted
`YYYY-MM-DD` across calendar days. Same-day slots must end after the current
local time; all other slots must be on or after the current local date.

Slot updates and deletes use conditional writes matching the originally read
date, times, booking flag, and status. A stale operation fails with a reload
error and does not write an audit record. Serializable transactions remain in
place for slot CRUD and booking interactions. Active bookings are checked by
space/date/time, while cancelled, rejected, and waitlisted bookings do not
keep slots reserved. Public booking creation still independently requires an
approved active listing and atomically marks the selected slot booked.

## Property photo management

Property photos use the existing ordered `Space.photos` JSON field. Each entry
stores server-generated metadata (`id`, storage `path`, original filename,
size, and MIME type); client-provided URLs and paths are ignored. The server
resolves public URLs from those paths when normalizing listing responses.

Owners manage photos through:

- `POST /owner/spaces/:id/photos`
- `POST /owner/spaces/:id/photos/:photoId/replace`
- `POST /owner/spaces/:id/photos/:photoId/delete`

Operations verify the authenticated owner and require an approved active
listing. JPEG, PNG, and WebP files are checked by extension, MIME type, and
signature. Each file is limited to 8 MB, uploads are limited to 8 files per
request, and listings are limited to 12 photos. New objects are uploaded
before database updates; failed updates remove only newly uploaded objects.
Replacements remove the old object only after a successful database update.
Deletion preserves the database result if storage cleanup fails. Conditional
`updatedAt` updates and transaction-local audits protect concurrent changes.

The required separate public Supabase bucket is `property-photos`. It must be
created with public object read access and server-side upload/delete
permissions using the existing server storage variables. The bucket was not
verified or modified in this environment. Ownership documents continue using
the private `ownership-documents` bucket.

## Owner listing edits and re-review

Owners may edit their own pending listings without clearing their existing
review metadata. Rejected listings still require a replacement ownership
document before resubmission; resubmission returns them to pending and clears
the previous review metadata.

Material edits to an approved listing, including property details, pricing,
allowed purposes, facilities, rules, or an ownership document, automatically
return the listing to `pending` and set it inactive. The service updates the
submission timestamp, clears the previous reviewer, review timestamp, and
rejection reason, and records a `resubmit_listing` audit event. The listing is
therefore hidden from public discovery and unavailable for booking until an
administrator approves it again. Unchanged submitted values do not trigger
this transition.

Owner updates use a transaction-local optimistic concurrency check over the
listing lifecycle and ownership-document state. If an administrator or another
update changes the listing after the owner loaded it, the update is rejected
and no listing or audit record is written. Uploaded replacement documents are
cleaned up on failed database updates without deleting the previous document.

## Milestone 5 operational workflows

User booking reads and mutations are now database-backed:

- `POST /bookings` calls `bookingService.create` and atomically reserves the
  selected availability slot.
- `POST /bookings/:id/cancel` calls `bookingService.cancel`.
- `POST /bookings/:id/extend` calls `bookingService.requestExtension`.
- `POST /bookings/:id/edit` calls `bookingService.edit`.
- `GET /bookings/:id/receipt`, `GET /my-bookings`, and `GET /history` use
  owner/user-scoped booking service reads.
- Waitlist join and leave routes call `joinWaitlist` and `leaveWaitlist`.

The public booking form now submits a server-provided availability-slot ID.
The service still validates the space, listing lifecycle, slot state, active
booking limits, weekly limits, allowed purpose, capacity, overlap, and
financial fields; client-provided prices and statuses are ignored.

Owner operational actions are connected through authenticated owner-scoped
routes:

- `POST /owner/checkin/:id` -> `bookingService.checkin`
- `POST /owner/return/:id` -> `bookingService.return`
- `POST /owner/today/:id/no-show` -> `bookingService.markNoShow`
- `POST /owner/bookings/:id/mark-paid` -> `bookingService.markPaymentReceived`
- `POST /owner/bookings/:id/approve-extension` ->
  `bookingService.approveExtension`
- `POST /owner/bookings/:id/reject-extension` ->
  `bookingService.rejectExtension`
- `POST /owner/today/:id/flag` -> `incidentService.createFromReturn`
- `POST /owner/incidents/:id/confirm` -> `incidentService.confirm`
- `POST /owner/incidents/:id/waive` -> `incidentService.waive`

Check-in transitions `approved` to `checked_in`; clean checkout transitions
`checked_in`/`overdue` to `returned` and applies the existing configured clean
return score adjustment; an unclean checkout transitions to `damaged` and
leaves the deposit held. Condition reports, notifications, score events,
audit records, payment state, and incident settlement are transaction-local.
Repeated or invalid transitions and cross-owner actions are rejected.
Extensions are limited to one or two hours, only apply during an active
checked-in session, reject midnight overflow and overlapping bookings, and
use conditional updates to reject stale retries. No new payment, refund,
payout, or scoring formula was introduced.

Users can report authorized booking incidents through
`POST /bookings/:id/incident`. The service accepts only the participating
user or owning owner, rejects unsupported booking states and duplicate pending
reports, and stores evidence fields without trusting client ownership data.
Owner incident confirmation/waiver remains the only path that changes deposit
settlement and configured damage score behavior.

Notifications are read through `notificationService.getUserNotifications`.
Mark-read updates require both notification ID and authenticated user ID;
mark-all is user-scoped. Booking, extension, check-in/return, no-show, and
incident settlement events create transaction-local notifications. Successful
mutations create audit records; failed or stale operations do not.

Completed/closed booking ratings are connected through
`POST /bookings/:id/rate` and `scoreService.rateBooking`. Only the booking
user may submit one integer rating from 1 to 5, and the schema's unique
booking constraint plus a transaction prevents duplicates. Ratings are
audited but do not alter reliability scores because the existing documented
score formula has no rating component.

`GET /my-score` and `POST /disputes` now use the score service. Admin dispute
reads and resolution use `scoreService.getDisputes` and
`resolveDispute`; resolution records the authenticated admin, updates score
only for accepted disputes using the existing formula, and writes an audit
record.

Focused operational coverage is provided by:

The suite covers owner authorization, check-in, repeated transitions,
extensions, incident participation, rating eligibility and duplicates,
notification isolation, and audit behavior. Existing route, authentication,

## Milestone 6 security hardening

Implemented controls:

- `middleware/csrf.js` generates a cryptographically random token per session
  and validates every POST, PUT, PATCH, and DELETE request. Multipart owner
  uploads validate after their upload parser completes.
- Authentication sessions regenerate after password and development demo login.
  Logout destroys the server-side session and expires the cookie.
- Session cookies are `HttpOnly`, `SameSite=Lax`, time-limited, and marked
  `Secure` when `NODE_ENV=production`. JSON and URL-encoded request bodies are
  capped at 100 KB.
- Suspended users are invalidated by the authentication middleware.
- Login and registration have in-memory per-IP route rate limits. The
  development-only demo shortcut is POST-only, CSRF-protected, and disabled
  in production.
- Signup roles are restricted to `user` and `owner`; service-layer update
  methods continue to whitelist mutable fields and derive ownership from the
  authenticated session.
- The production error page no longer renders exception messages. Detailed
  errors remain server-side only.

Focused security coverage:

```text
node scripts/testSecurity.js
```

Deployment requirements and remaining risks:

- Run behind HTTPS with `NODE_ENV=production`; verify proxy/TLS configuration
  before enabling secure cookies.
- Replace the process-local session and rate-limit maps with a shared,
  expiring store before running multiple application instances.
- Configure Supabase bucket policies through the approved infrastructure
  process; this milestone does not change bucket settings.
- Review server logs and access controls before production because development
  mock data and demo accounts must not be enabled in production.
